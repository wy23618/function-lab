考研数学函数可视化工具
Codex 完整开发提示词
产品需求 · 父子 Agent 执行规划 · 额度与对话优化
建议直接将本文件整体交给 Codex 作为项目总需求。
使用方式
1.  如果项目为空，让父 Agent 先初始化 React + TypeScript + Vite；如果已有项目，则先读取现有结构并继续开发。
2.  父 Agent 使用 Sol，负责架构、数学正确性、任务拆分、集成和最终验收。
3.  边界清晰的局部任务优先交给 Luna 6.1 子 Agent；若环境暂时不支持指定模型，则使用可用的低成本执行模型，但不要改变总控原则。
4.  开发过程中持续维护 docs/DEVELOPMENT_STATE.md 和 docs/TASKS.md，减少重复扫描代码库和重复对话。
5.  每个阶段先做最小可用闭环，再进入下一阶段；不要为了“多功能”牺牲数学正确性和操作简洁性。

第一部分｜产品与功能需求提示词
1. 产品目标与核心工作流
用户输入函数后立即绘制，不要求再经过复杂确认。
选择一个函数后，可以通过“对称、反函数、平移、伸缩、绝对值、奇偶性”等中文按钮直接操作。
执行数学变换后，原函数默认保留，新函数自动分配明显不同的颜色，便于叠加比较。
任何数学操作都要联动显示：原函数 → 变换规则 → 新函数/新关系 → 几何意义。
软件要让“公式看不懂时看图，图看不懂时看公式”，而不是只给结果。
2. 函数输入与数学键盘
支持 y=x^2、f(x)=x^2、sin(x)、cos(x)、tan(x)、e^x、ln(x)、log(x)、sqrt(x)、abs(x)、1/x 等常见表达式。
尽量兼容自然数学输入：sin x、sin(x)、y=sin(x)、f(x)=sin(x) 都应尽量正确识别。
支持 π/pi、e、指数、分数、括号、绝对值、根号、常见三角函数与反三角函数。
必须提供专门的数学键盘/符号面板，让用户无需依赖系统输入法即可输入 π、√、^、|x|、sin、cos、tan、ln、log、分式、括号等。
输入错误时给人类可读提示，如“可能缺少右括号”，不要直接抛出程序异常。
输入框与数学键盘要服务于高频操作，不做复杂公式编辑器式的笨重交互。
3. 多函数比较
允许同时添加多个函数并叠加在同一坐标系。
左侧函数列表至少包含：颜色、函数名、表达式、显示/隐藏、删除、复制、编辑、锁定、颜色选择。
默认自动分配舒服、清晰、彼此可区分的颜色；避免刺眼配色。
点击函数后将其设为“当前函数”，后续数学操作默认作用于当前函数。
允许快速只看某一函数、恢复全部函数、自动适应所有可见函数。
4. 核心函数变换工具栏
关于 Y 轴对称：f(x) → f(-x)，显示“x → -x”。
关于 X 轴对称：f(x) → -f(x)，显示“y → -y”。
关于原点对称：f(x) → -f(-x)。
关于 y=x 对称：进行几何镜像，同时显示浅色虚线 y=x。
关于 y=-x 对称：作为常用快捷操作。
变换后保留原函数，并生成独立的新函数/关系对象，允许单独隐藏或删除。
5. 反函数
提供独立“反函数”按钮，并同时显示原函数、y=x 与反函数/镜像关系。
先检查当前定义域内是否一一对应；如果不是，明确提示“当前定义域下不存在完整反函数”。
允许用户直接限制定义域后重新尝试，例如 y=x², x≥0 → f⁻¹(x)=√x。
如果无法符号求解，可先显示几何镜像，但 UI 必须明确区分“镜像关系”和“真正的反函数”。
反函数的定义域、值域交换关系应作为可视化解释的一部分。
6. 平移与伸缩
平移支持横向参数 a 与纵向参数 b，实时显示 f(x-a)+b。
支持滑块和数值输入；拖动时图像实时变化。
动态解释“向右 2 → f(x-2)”“向上 3 → f(x)+3”。
伸缩支持 y=A·f(x) 与 y=f(Bx)，使用滑块实时变化。
解释 A>1、0<A<1、A<0，以及 B 变化对应的纵向/横向伸缩与翻折。
始终把图像变化、公式变化、文字解释放在同一观察路径中。
7. 绝对值变换
提供 |f(x)|、f(|x|)、-|f(x)|、|f(|x|)| 等高频操作。
|f(x)|：X 轴下方部分翻折到上方。
f(|x|)：保留右半部分并关于 Y 轴复制到左侧。
操作后同时显示原图与变换图，便于直观看出哪些局部发生了变化。
8. 任意对称与点工具
快捷支持 X 轴、Y 轴、原点、y=x、y=-x。
自定义支持 x=a、y=b、y=kx+b、Ax+By+C=0。
对于一般直线对称，不强求最终必须是显函数；可以对采样点进行几何反射，保证图像结果正确。
点工具允许在图中点击 A(x,y)，显示关于指定轴/直线的 A′，并画出必要的垂线或参考线。
点、原点、对称点、对称轴的视觉关系要清楚，不要让辅助线喧宾夺主。
9. 数学分析工具
奇偶性：比较 f(x)、f(-x)、-f(x)，并通过叠图说明为什么是奇/偶函数。
零点：标记与 X 轴交点。
交点：选择两个函数求交点并标注坐标。
定义域：支持 x>0、x≥0、-2≤x≤5 等限制，并与反函数功能联动。
值域：可以作为后续功能，架构上预留。
导数、极值、单调性、切线、法线、渐近线等作为后续分析模块。
切线：用户选择 x=x₀ 后显示点、f′(x₀) 和切线方程，并直接绘制切线。
10. 图像交互
鼠标滚轮缩放、拖动画布、恢复默认视图、自动适应全部可见函数。
默认 X/Y 坐标单位长度一致，避免视觉变形。
显示/隐藏网格、坐标轴、刻度；支持全屏。
鼠标移到曲线上显示 x、y 与十字参考线；点击可固定观察点。
允许添加多个观察点，便于比较。
缩放后重新采样，确保高频函数与渐近线附近仍正确。
11. 绘图算法与不连续性
不能只用少量固定点连接成折线；使用合理的自适应采样或足够稳健的分段采样。
sqrt(x) 不绘制 x<0；ln(x) 不绘制 x≤0；1/x 在 x=0 断开；tan(x) 在渐近线两侧断开。
不能把不连续点两侧错误连接成穿越画布的直线。
对 1/(x-2)、sin(10x) 等情况进行专门测试。
当用户缩放时，根据新的可视范围重采样。
12. 数学术语操作与 Command Palette
右侧数学工具按“变换 / 分析 / 几何”分组。
提供 Ctrl+K 命令面板，可搜索“Y轴”“反函数”“切线”“定义域”等中文术语直接执行。
不要要求用户记住程序员式命令；UI 同时显示标准数学符号。
常用操作最多 1～2 次点击完成。
13. 变换历史
连续变换要记录完整历史，支持撤销/重做。
每个生成函数保存 parentFunctionId 和 transformHistory。
示例：f(x)=x² → 关于Y轴 → 向右2 → 向上3；历史中能看到每一步公式变化。
历史的目标是帮助学习变换链，而不是做复杂版本控制。
14. 页面布局与视觉设计
桌面端推荐三栏：左侧函数列表；中间大坐标系；右侧当前函数的数学工具。
中间图像区域占最大视觉面积，是整个产品的绝对中心。
右侧工具面板可折叠，避免挤压图像。
风格现代、简洁、舒服，有数学工具/IDE 的克制感；可参考 Desmos / GeoGebra 的简洁原则，但不要照搬。
避免巨大标题、大量渐变、花哨动效、每块内容都做卡片、过多阴影。
建议浅灰白背景、白色面板、轻边框、8～12px 圆角，函数颜色作为主要视觉强调。
15. 操作原则
输入后直接绘制。
一个数学变换尽量不超过两次点击。
原函数默认保留。
生成函数自动分配新颜色。
用户随时可隐藏任意函数。
数学术语使用中文，同时显示标准数学表达式。
不要让用户先学会软件才能学数学。
16. 技术建议与工程结构
优先做本地 Web 应用：React + TypeScript + Vite。
数学解析、符号运算和绘图可选择成熟开源库；不要依赖付费 API Key 才能使用核心功能。
数学计算与 UI 分离，避免所有逻辑堆在组件里。
项目至少应包含 components、services、types、utils、tests 等清晰模块。
17. 内部函数模型
每个函数建议保存：id、name、originalExpression、currentExpression、color、visible、domain、lineStyle、parentFunctionId、transformHistory。
每个生成函数知道“来自谁、经过什么变换”。
TransformOperation 使用统一类型定义，避免不同模块各自发明数据结构。
对“不能表示为 y=f(x) 的镜像关系”应允许使用 relation/implicit curve 类型，而不是强行塞回 FunctionDefinition。
第二部分｜父子 Agent 执行规划
18. 模型角色
父 Agent：Sol。唯一总负责人，掌握完整需求、架构和项目状态。
子 Agent：优先 Luna 6.1。用于局部实现、测试、UI细节、文件分析等明确任务。
如果环境不支持直接指定 Luna 6.1，不要停止开发；选择可用的低成本执行模型，并继续由 Sol 总控。
19. 父 Agent（Sol）职责
理解完整需求并维护产品边界。
确定技术架构、公共接口、核心数据模型。
拆分 Phase 与任务，并判断哪些任务适合并行。
负责复杂数学正确性：反函数、定义域、一一对应、任意直线对称、采样与不连续性。
处理跨模块问题、复杂 Bug、性能瓶颈和重大重构。
审核子 Agent diff，做最终集成与完整测试。
控制上下文规模和总额度消耗。
20. 子 Agent（Luna 6.1）适合的任务
FunctionList 等边界清晰的 UI 组件。
简单 CSS、布局、响应式、overflow 修复。
表达式 parser 的局部规则实现。
X轴/Y轴/原点对称等已确定接口后的基础 transform。
单元测试、类型补全、简单重构、文档同步。
运行局部测试并根据明确错误做局部修复。
检查页面基础可用性、按钮可见性、布局错位。
21. 不适合直接下放的任务
核心数据结构设计。
绘图采样算法总设计。
反函数数学判定总设计。
跨多个模块的大规模重构。
多个 Agent 同时改 GraphCanvas / 全局状态。
需要完整产品背景才能做决定的任务。
22. 子 Agent 数量与并行规则
默认同时 2～4 个子 Agent；简单阶段 0～1 个即可。
只有真正独立的任务才能并行。
父 Agent 必须先确定公共接口，再允许多个 Agent 并行实现。
禁止多个 Agent 同时修改同一核心文件。
禁止十几个 Agent 同时“探索项目”。
禁止让多个 Agent 重复完成同一个任务。
23. 子 Agent 任务下发格式
不要把整份超长需求反复发送给子 Agent。
每个子任务只提供：目标、相关文件、相关接口、限制条件、验收条件。
任务必须小而明确，最好可以独立验证。
24. 子 Agent 回报格式
完成了什么。
修改了哪些文件。
运行了哪些测试，结果如何。
是否存在风险。
是否需要父 Agent 决策。
禁止重复项目背景、完整需求和长篇开发日志。
25. 推荐 Agent 工作流
1.  Sol 读取当前项目状态。
2.  Sol 确定本阶段目标和公共接口。
3.  Sol 把独立任务拆成 2～4 个子任务。
4.  Luna 6.1 子 Agent 并行完成局部实现。
5.  Sol 优先查看 git diff、修改文件列表和测试结果。
6.  Sol 只深入阅读核心逻辑或出现问题的文件。
7.  运行阶段级测试与完整构建。
8.  更新 DEVELOPMENT_STATE.md 和 TASKS.md。
9.  给用户发送简短阶段报告，然后进入下一阶段。
第三部分｜额度消耗、上下文与对话优化
26. Sol 额度应该花在哪里
架构决策与公共接口。
复杂数学推理和边界条件。
复杂 Bug 与跨模块状态同步。
性能瓶颈与采样算法。
代码 Review 与最终集成。
子 Agent 连续失败后的重新分析。
27. 不要浪费 Sol 的任务
全文搜索、目录浏览、查变量。
批量改变量名、整理 imports、格式化。
重复跑测试。
简单 CSS 调整。
机械拆组件。
明显局部的小修复。
28. 工具优先
搜索文件、搜索变量、查看目录、查看 git diff、运行测试、读取错误日志、格式化等，优先直接用工具。
Agent 用于“需要理解后修改”的任务，不要为了用 Agent 而用 Agent。
能通过一次工具调用获得的事实，不要创建一个子 Agent 去调查。
29. DEVELOPMENT_STATE.md
记录当前架构、当前 Phase、已完成模块、关键接口、重要技术决策、已知问题、测试状态。
内容必须短、结构化，只保存长期有价值的信息。
不要记录完整聊天记录或每次命令日志。
恢复上下文时优先读取它，而不是重新扫描整个仓库。
30. TASKS.md
31. 上下文控制
不要把整个 repository 塞给每个 Agent。
先搜索相关文件，只读取当前任务真正需要的内容。
例如实现 inverseEngine，只读取相关 type、parser、transform、tests，不读取全部 UI/CSS。
每完成一个 Phase，把长期状态写回 DEVELOPMENT_STATE.md，减少后续重新理解成本。
32. Diff 驱动 Review
子 Agent 完成后，Sol 先看 git diff、修改文件列表、测试结果。
如果 diff 很局部且合理，不需要重新阅读全文。
重点检查核心算法、接口变化、数学逻辑。
发现问题后再按需展开具体文件。
33. 测试分层
1.  局部修改后只跑相关单测。
2.  一个功能组完成后跑模块级测试。
3.  一个 Phase 完成后跑 unit tests + TypeScript + lint + build。
4.  最终交付前再做完整检查。
34. 失败重试限制
同一个子 Agent 连续两次无法解决同一问题，就停止无限重试。
升级给 Sol，重新分析错误日志、设计问题和任务拆分。
禁止“随机改代码 → 测试失败 → 再随机改”的循环。
35. Bug 处理流程
优先最小必要修改。
不要因为修一个 Bug 顺手重构十几个无关文件。
非必要重构记录到 TASKS.md，后续处理。
36. 优化与用户的对话
不存在真正阻塞时不要频繁询问用户。
按钮间距、变量名、文件名、普通组件拆分、轻微 UI 调整等自主决定。
只有产品方向明显改变、需求冲突、需要付费服务、核心技术栈变化等情况才需要用户决策。
不要每一步都输出“我现在准备……/下一步我将……”。
只在重要节点报告：开始哪个阶段、发现重大问题、阶段完成、是否需要用户决策。
禁止把父子 Agent 的内部长对话原样展示给用户。

核心目标
做一个“考研数学函数可视化实验台”：输入函数后立即得到图像；通过中文数学术语一键执行对称、反函数、平移、伸缩、绝对值、奇偶性等操作；原图与变换图可同时对比；公式变化、图形变化和几何意义始终联动。
产品定位
不是普通函数画图器，而是面向考研数学学习的“函数实验室”。最高优先级：图像是视觉中心；数学术语操作简单；多个函数对比直接；任何变换都同时给出公式、图像与几何解释。
输入函数 → 自动解析 → 立即绘图 → 选择数学操作 → 生成新函数/几何关系 → 原图与新图同时对比 → 显示数学解释

数学严谨性提醒
“关于 y=x 对称”与“存在反函数”不是同一个概念。完整 y=x² 关于 y=x 的镜像是 x=y²，这是一条关系，不应直接称为 y=√x 的反函数。只有先限制定义域（如 x≥0）并满足一一对应，才能生成真正的反函数。
